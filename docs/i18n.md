# Internationalization

VisualDXPBuilder ships an English catalog and a typed translation contract. Your application owns which languages are available, their translations, loading resources, and selecting the active language. There is no global locale, automatic language detection, or required translation-library dependency.

```tsx
import { useState } from 'react';
import {
  VisualDXPBuilder,
  type BuilderMessages,
  type Workflow,
} from 'dlb-dxp';
import 'dlb-dxp/styles.css';

// Keep catalogs outside render, or memoize them when adapting another library.
const spanish = {
  'common.cancel': 'Cancelar',
  'website.save': 'Guardar sitio web',
  'canvas.zoomIn': 'Acercar',
  'canvas.zoomOut': 'Alejar',
  'nodes.delay.label': 'Espera',
  'nodes.delay.description': 'Hace una pausa antes de continuar.',
  'canvas.nodeCount': ({ count }) =>
    `${count} ${count === 1 ? 'nodo' : 'nodos'}`,
  'activity.nodeAdded': ({ label }) => `Se añadió «${label}»`,
} satisfies Partial<BuilderMessages>;

export function Editor({ workflow }: { workflow: Workflow }) {
  const [locale, setLocale] = useState('en');
  return (
    <>
      <select
        aria-label="Editor language"
        value={locale}
        onChange={(event) => setLocale(event.target.value)}
      >
        <option value="en">English</option>
        <option value="es-ES">Español</option>
      </select>
      <div style={{ height: 700 }}>
        <VisualDXPBuilder
          initialWorkflow={workflow}
          i18n={{
            locale,
            direction: 'ltr',
            messages: locale === 'es-ES' ? spanish : undefined,
          }}
        />
      </div>
    </>
  );
}
```

This is an intentionally partial Spanish example. Omitted keys use their English defaults. Exported `englishMessages` lists the complete catalog, including formatter functions and their parameter names. Use `satisfies BuilderMessages` instead of `Partial<BuilderMessages>` to require complete coverage when upgrading the package. Keys are stable identifiers; changing English copy does not require changing a key.

## Message values and formatting

Static messages are strings. Dynamic messages are functions returning strings, with parameters inferred from the key. The host controls word order, plural rules, and formatting inside those functions. For languages with more than two plural categories, use your translation library or `Intl.PluralRules`; do not assume `count === 1` works for every language. A formatter can close over `Intl.NumberFormat(locale)` for localized numbers.

Messages render as React text, not HTML. Keep rich workflow content in the workflow itself. The catalog does not control script URLs, CSS selectors, node kinds, connection IDs, or the preview bridge's generated HTML.

`locale` is a valid BCP 47 tag (default `en`). It controls activity dates/times, the zoom percentage, and the builder root's `lang` attribute. `direction` defaults to `ltr`; set it explicitly to `rtl` for a right-to-left editor. Text and editor chrome follow this direction, while graph coordinates and connection handles retain their existing left-to-right semantics. The host should test its completed translations for text length and layout.

Changing `i18n` updates the mounted editor. Do not change its React `key` to change languages: remounting would reset editor state. Separate instances may use separate languages. Treat message catalogs as immutable and supply a new object when changing translations.

## Using an existing translation library

Map the typed messages to your application's translator. For example, with an already-configured i18next instance:

```tsx
const messages = useMemo(() => ({
  'common.cancel': t('builder.cancel'),
  'canvas.nodeCount': ({ count }) => t('builder.nodeCount', { count }),
  'activity.nodeAdded': ({ label }) => t('builder.nodeAdded', { label }),
}) satisfies Partial<BuilderMessages>, [t, locale]);

<VisualDXPBuilder i18n={{ locale, messages }} />
```

Configure plural resources and React-safe interpolation in the host's library. The builder does not install, initialize, or mutate that library. When loading a language asynchronously, the host can keep the previous catalog or show its own loading state until the new one is ready.

## Authored content and activity

Switching editor language does not rewrite workflow names, existing node/connection labels, notes, HTML, preset content, or configuration values. A newly added node receives its localized default label once; that label then becomes ordinary editable workflow content. The bundled common DXP presets include English and Spanish content in `src/presets/locale`. Their cards and newly applied workflows follow the editor locale (`es` and regional variants such as `es-ES`); other languages fall back to English. This includes names, descriptions, node and connection labels, setup notes, and visitor-facing content. Host-authored or customized presets and initial sample workflows remain supplied content and should be translated by the host when desired. Assistant replies, external server messages, and execution logs are output from their respective services/runtime and are not automatically translated by the editor catalog.

Builder-generated activity contains an English `action` snapshot plus a serializable `message: { key, params }`. Persist the entire entry, including `message`. The activity panel resolves that message in the viewer's current language. Usernames and values such as node names remain unchanged. `action` is also available for search and host-authored free-text activity. No record migration is performed.

```ts
import { createBuilderTranslator, formatActivity } from 'dlb-dxp';

const translate = createBuilderTranslator(spanish);
const textForViewer = formatActivity(activityEntry, translate);
```

## Validation and standalone components

Pass a translator to `validateWorkflow(workflow, translate)` to localize validation messages outside the builder. Issues that affect editor behavior expose stable codes, such as `workflow.cycle`; do not branch on translated prose. `formatBuilderError(error, translate)` formats structured errors from bundled helpers; unknown errors retain their original text.

The separately exported `ElementPicker` can inherit the same context:

```tsx
import { BuilderI18nProvider, ElementPicker } from 'dlb-dxp';

<BuilderI18nProvider i18n={{ locale: 'es-ES', messages: spanish }}>
  <ElementPicker url={websiteUrl} onSelect={selectElement} onClose={closePicker} />
</BuilderI18nProvider>
```

## Bundled preset catalogs

`commonDXPPresets` and the individual preset exports retain their original English content. Use `getCommonDXPPresets(locale)` to select translated presets outside the editor:

```ts
import { getCommonDXPPresets } from 'dlb-dxp';

const presets = getCommonDXPPresets('es-ES');
```

The exported `englishPresetMessages`, `spanishPresetMessages`, and `PresetMessages` type describe the complete preset copy. Preset locale resources are separate from editor chrome messages. Changing the editor language does not rewrite a workflow that has already been applied or edited.
